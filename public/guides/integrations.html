Integrations

Show what an agent is doing in the office without giving the panel control of the agent. Your connector observes the engine, opens a visit and reports activity over HTTP. This guide is public; reading it grants no office access.

Ask an agent to integrate another engine

Give the agent the instructions below. If it runs on another machine, use a panel address it can reach; its loopback address is not yours. Share only the public guide URL, never a dashboard or office share link.

Read the AgentMiniOffice integration guide at /guides/integrations.html (on my panel’s origin). Identify the lifecycle and tool events my engine exposes. Choose an extension, plugin or application for background reporting, or a skill for a single explicitly observed action. Tell me which events you cannot observe. Implement only supported reports. Keep credentials in private configuration, not in chat. Verify one visit, a heartbeat, an accepted action and an exact retry in a disposable office. Do not enable reporting in my active installation.

A skill that calls an API can send an event. It cannot promise periodic presence or observe a slash command unless its host exposes that information. Test a real hook before mapping it.

Report an Action from Any Client

Your sender chooses the action; the office chooses the station, route and gesture. A plugin, extension, ordinary application or skill running curl can send the same authenticated JSON. No Pi installation, tool name or panel change is required. Report only work you observed, not prompts, answers, file paths or tool arguments.

Download action schema and catalogue (JSON) — x-actions lists each ID, room, pose and label. For example, lookup_file prefers a filing cabinet; search_content prefers a bookshelf. Use note for an observation with no tool, or set data.action on tool.start or tool.call.

Action field reference

The schema validates data.action, not the event envelope. Its JSON type is string, length 1–48, pattern ^[a-z][a-z0-9_]*$. A tool reporting one completed content search can send type: tool.call and data.action: search_content even when the tool has a private name.

Station and pose variants

What a connector can send: one observed data.action with an optional data.variant from that action’s catalogue entry, or an optional event-level room hint. Valid room IDs are lobby, barber, desk, whiteboard, library, workshop, print-room, phone-booth, meeting, pantry, intern-desk and away. An explicit action takes precedence over the hint. Neither field accepts a comma-separated list of choices.

What the panel chooses: an available physical slot for the requested variant, its base pose on arrival, and any listed brief gestures. Without a variant the panel chooses automatically. The names below describe the current renderer; they are not commands. For example, board-writing is a station, not a room ID; scan is a gesture, not an action ID.

How catalogue variants work

Variants are optional annotations under x-actions in the panel catalogue (download JSON). All senders use the same catalogue. Do not send a variants array in telemetry or put one in a Pi tool map. Send {"action":"search_web"} for automatic assignment, or {"action":"search_web","variant":"laptop_typing"} to request the laptop even when the bookshelf is free. If there is no spare laptop, the avatar can use the search bookshelf or cabinet. The panel tries the requested variant, its listed fallback IDs, then the same action’s remaining working and overflow entries, skipping duplicates. The map needs no fallback list. If every compatible place is busy, the avatar keeps its activity label and waits without a prop, occasionally glancing or tilting its head unless reduced motion is enabled. The preferred station is reclaimed when available. An invalid pair is rejected with invalid_variant.

{"id":"shelf_reading","when":"working","room":"library","object":"bookshelf","poses":["reading","scan","lean"],"fallback":["cabinet_paper"]}

The first pose is the base interaction. Later entries are optional brief gestures, selected using the avatar’s seed and settled scene time rather than rerolled on each heartbeat. A working entry is a preferred station, an overflow entry is a fallback when preferred stations are occupied, and a work_trip entry permits a temporary visit during sustained work. A different visual room does not change the reported room or action. Idle, human attention, final responses and reduced motion keep their separate rules. Only objects and poses supported by the renderer are usable.

Visual analysis can inspect the whiteboard (board_inspection) or move the mouse at a spare desk (desk_mouse), without typing. Reading, content search and file lookup can read a book or sort material at a cabinet (cabinet_reading, cabinet_sorting), move a mouse or arrange desk papers (desk_documents). See the JSON for exact IDs, gestures and fallbacks for each action. Final overlays and other activity have no selectable variant.

Send one observed action

First open a visit and send a heartbeat. Set ORIGIN to the verified panel origin and AGENT_ID to the ID from session open. Supply WRITER privately. Generate a fresh lowercase UUIDv7 for EVENT_ID and set SEQ to the next integer across heartbeats and events. Keep both values and the payload unchanged if retrying this report.

printf 'Authorization: Bearer %s\n' "$WRITER" | curl --fail-with-body --silent --show-error --max-time 10 \
  --header @- --header 'Content-Type: application/json' \
  --data-binary "{\"events\":[{\"event_id\":\"$EVENT_ID\",\"seq\":$SEQ,\"type\":\"note\",\"data\":{\"action\":\"lookup_file\"}}]}" \
  "$ORIGIN/api/v1/agents/$AGENT_ID/events"

Check that rejected is empty even on HTTP 200. An explicit action takes precedence over a tool or valid room hint. An unfamiliar but valid ID becomes other: the avatar can interact with an available plant, aquarium or board under the label Other Activity. It does not invent a phone call, print job or plan. IDs are 1–48 lowercase ASCII letters, digits or underscores and must start with a letter. A malformed ID or an action on another event type is rejected with invalid_action. Without an action, an explicit room wins; otherwise tool events use the common defaults.

For a real compaction start, send a note with data.action: compact_context and keep the heartbeat working while the operation is active. On completion, cancellation or failure send an outcome note and the current heartbeat state. No context contents are needed.

After a confirmed final response, send final_response for either available prop, final_print for the printer only, or final_call for the handset only. Report idle normally. The optional visual beat does not acknowledge delivery or occupy a busy station.

Optional Connector: Pi

Download Pi connector (.zip)

Install in one scope

Choose ~/.pi/agent/ (or your configured Pi agent directory) for global use, or <workspace>/.pi/ for one trusted project. Extract the ZIP into extensions/ under that root. It already contains the enclosing folder. Check the resulting layout:

Pi root/
  agent-mini-office.json                 private settings, created on load
  extensions/agent-mini-office/
    index.ts                             hooks and HTTP sender
    actions.json                         editable, active tool mappings
    actions.example.json                 optional examples; not loaded
    actions.schema.json                  validates the map
    action-v1.json                       local catalogue and action schema

Compatibility: The panel accepts the REST contract, not a particular Pi filename. Both current downloads send explicit actions. Older connectors can still report tool events without an action. The same small set of common defaults applies to all engines. Prefer the ZIP for new installs.

Upgrading from one file? Stop reporting and move the old agent-mini-office.ts (or undashed entry) outside Pi’s extension search paths before reloading. Keep the private settings in the same root. Start with the packaged actions.json. Copy the overrides you want to keep from the old root agent-mini-office.actions.json: for the same source and tool name, replace the packaged action with your custom action. Add new pairs and leave all other packaged entries unchanged. The folder entry never reads the old override. Back up your edited map before replacing the folder in future updates. Install one entry only. For existing single-file workflows, the legacy single-file download (.ts) still uses the optional root override and its original defaults.

Connect and verify

  1. For project-only use, exclude /.pi/agent-mini-office.json* from Git before setup. Do not load both the project and global extension in the same session.
  2. Run /reload in Pi. Open /agent-mini-office, choose Update Panel URL, and enter the HTTPS origin of your panel (HTTP is supported on loopback).
  3. Choose Update Token and paste the office join key or a trusted connector credential into the Pi input field.
  4. Choose On to start reporting. Use /agent-mini-office off to stop. Telemetry starts off on a new installation. Changing the panel URL clears the old token and switches reporting off.

In Dashboard → Agents, look for your folder name with harness Pi. Invoke a registered read tool and check the inspector’s reported action and source. A visible card verifies the visit; an action verifies the tool hook. A short event need not move the avatar.

Assign a task to an idle Pi session

Use a Trusted token issued with Inbox access. A join key, a Trusted token without Inbox, or an older collector that omits the grant enables telemetry only. There is no separate Pi task setting. On the dashboard, assign a task to the intended visit, not just a matching folder name. Its title and brief become a user message in that Pi session and are sent to its configured model. Only grant Inbox to a panel you trust to submit work. Pi’s usual approval rules still apply; answer any prompts in Pi.

Todo means stored, not delivered. Pi checks for one task when idle, without queued input or an open prompt. The visit has 15 minutes from creation to claim it. Doing means claimed: Pi renews a separate execution lease while working. Done shows the outcome. Pi acknowledges only when the task turn ends normally with PANEL-TASK-DONE <task-id> on its final line. An abort or missing receipt fails the task, not a success. The panel gets a fixed result, not the conversation. If the session disappears, the lease can expire. A new visit does not inherit old tasks.

The menu also accepts /agent-mini-office url, /agent-mini-office token, and /agent-mini-office on. Loading the extension creates agent-mini-office.json directly in the chosen Pi root if the file does not exist. Edit these settings in the file or use the menu. Reloading preserves existing settings. Defaults:

{"enabled": false, "panelUrl": "http://127.0.0.1:3000", "token": "", "maxRetries": 3}

The token selects the office. For first-time enrollment with a join key, the Owner must open admission. No office or project setting is required. The project label follows the Pi session name (/name); an unnamed session uses the working folder's name. The label is visible to office viewers. New Pi avatars show the folder name alone; a linked Pi child displays Sub · <folder name>. The visit name comes from the working folder, never the full path, project title or UUID. Older connectors must be replaced in the chosen Pi scope and reloaded; the panel cannot reconstruct a folder that was never reported. Two visits in one folder have the same name and separate IDs.

Keep the JSON file private (mode 600). It contains only the four settings above. The writer and general enrollment proof stay in memory. Ordinary reports do not rewrite the file. To uninstall, close Pi and remove the extension and its JSON file. Revoke a General or Trusted connector in Workspace Access to remove all its sessions. Deleting or closing just one session revokes that connector only if no other session remains. When updating from the undashed filename, close older Pi sessions and replace the old extension rather than loading both. If the new config is absent, the extension moves the private agentminioffice.json to the new name, preserves the four settings (defaulting missing maxRetries to 3), and removes old session archives.

The sample sends presence on startup, approximately every 15 seconds, and on work/settled hooks. Tool start/end hooks send the mapped action, source, an allowlisted name (or “other”) and, on completion, a success flag. Pi UI prompt notifications report waiting/resumed and the prompt kind. A confirmation can display the fixed Yes / No options; private choice text, prompt titles and answers never leave Pi. Answer in Pi. Other engines can send the same standard display IDs; the office has no reply channel. Telemetry does not send prompts, paths, arguments, tool results or inferred run outcomes. Task receipts use the separate inbox API. Quit stops the timer. With the collector running at its defaults, a temporary visit loses its online status 30 seconds after its last heartbeat, becomes offline at 90 seconds and becomes eligible for cleanup after another 30 minutes by default. The next accepted heartbeat in that office clears expired sessions and their tasks, including older sessions without a visit marker. With no incoming heartbeat, an Owner can still delete an Offline session from Dashboard → Agents. Turning reporting off does not delete it immediately. Dedicated fixed-token workers have a separate retention period and can return without inheriting old tasks. Restarting Pi creates a new visit. After an HTTP or network failure, the extension names the failed operation and schedules retry N after N × 5 seconds. maxRetries is the number of additional attempts (default 3; 0–10). With the default, the delays are 5, 10 and 15 seconds. A successful report resets the counter. After exhaustion, this session stops sending until re-enabled or reloaded; other sessions continue independently. For enrollment 401, check the office key and Open admission. The server terminal logs API route templates and status codes; look for enrollment, session open, heartbeat and events. It retains an unconfirmed tool event for exact replay, not an offline history of everything Pi did while paused.

How Pi reports compaction and other activity

Only tool calls go through actions.json. A second path starts with a Pi session hook. Both paths use the same REST API; the panel never reads your Pi tool map.

  1. Pi observes the start. The connector’s index.ts listens to session_before_compact. It sends a working heartbeat and the event below. This is the event body inside the batch, with the ID and sequence omitted here; see the full request envelope.
{ "type": "note", "data": { "action": "compact_context" } }
  1. The collector reads the action. The compact_context entry in action-v1.json specifies the library, the sorting pose and the label “Compacting Context”. The action is published in the office stream and appears in the snapshot. No tool name or legacy fallback is involved.
  2. The scene shows the observation. If a cabinet is available, the avatar walks to it and sorts books on arrival. Reduced motion keeps the pose static. Pi’s session_compact or session_compact_failed hook sends a success, cancellation or failure note and updates presence. No summary or error text is sent.

Compare three other paths: calling the registered grep tool uses the map to send search_content; a normal final assistant response uses agent_end and agent_settled to send final_response; a Pi UI prompt sends the event human.waiting, not the action meet. You only edit the map for the first path.

Map a Pi Tool to an Action

Looking for compaction? actions.json maps tool calls only. Pi reports context compaction through session hooks in index.ts, not through a tool called “compact”. When compaction starts, the connector sends compact_context, which is listed in action-v1.json. No map entry is needed. Final responses and human-input waits also come from hooks, not from the tool map.

Example: pi-web-search registers web_search. If that is the effective extension tool in your Pi session, map it to the semantic action search_web. The ZIP’s active actions.json includes this pair. The separate actions.example.json below mixes automatic and explicitly selected variants. Copy only the entries you want into your existing map; the example is not loaded and does not include all default mappings. Do not edit index.ts or either schema.

{
  "$schema": "./actions.schema.json",
  "version": 1,
  "tools": {
    "builtin": {
      "read": { "action": "read", "variant": "cabinet_reading" },
      "grep": { "action": "search_content", "variant": "desk_mouse" },
      "find": { "action": "lookup_file", "variant": "cabinet_sorting" },
      "write": "write"
    },
    "extension": {
      "update_plan": { "action": "plan", "variant": "desk_documents" },
      "web_search": { "action": "search_web", "variant": "laptop_typing" }
    }
  }
}
Download variant mapping examples (JSON)

Map schema: version must be the number 1. Under tools, the allowed source keys are builtin, builtin-extension, extension, sdk and unknown. Each maps exact registered tool names (1–96 ASCII letters, digits, underscores, periods, colons or hyphens) to action strings or to an object such as "web_search": {"action":"search_web","variant":"laptop_typing"}. For explicit selections keep the downloaded action-v1.json next to the map (already included in the ZIP; for a flat install this is the Pi root). Both the connector and collector check membership. An invalid selection makes the local map invalid; it is not silently sent as an automatic choice. Extra top-level keys are not allowed. The optional $schema points your editor to the local schema. Download map schema (JSON); keep action-v1.json beside it for offline validation. Both ship in the ZIP.

Run /reload, invoke the tool, then inspect the visit. Expect Searching the Web with source Extension; custom tool names stay local. A mapping reuses an action; it does not create an animation or enable an unreported hook. Unmapped pairs yield other. A missing, invalid or larger-than-64-KiB package map disables all tool mappings for that load; restore the map and reload. Do not put credentials or private data in action values.

What a Pi visit actually shows

Pi 1.5.2 enables read, bash, edit and write by default. grep, find, ls and powershell are also core tools, but optional. The adapter does not enable tools. It checks the effective tool registration: core, shipped extension, installed extension, SDK or unknown. A replacement named read is not automatically a core tool. The agent inspector shows the reported source for tool signals. Only allowlisted names leave Pi; no source paths, commands, arguments or results are transmitted.

  • Laptop desk: edit and write. If desks stay full for three seconds, an available standing writing spot can be used without operating the printer.
  • Workshop: core bash and powershell report shell activity without interpreting the command. By default, unmapped tools report neutral other, not workshop activity.
  • Bookshelf vs filing cabinets: core read/grep prefer the bookshelf. Core find/ls prefer a free cabinet, even for a single visitor. Both can use another library station when full.
  • Installed extensions: inspect the effective tool registration before adding a source/name pair. Installing a package or invoking an invisible slash command is not a report of work.
  • Final Response: after Pi settles, a normal final assistant message with a text block emits one note with action final_response (legacy kind final-response). The connector checks message metadata, not response text. Tool calls, errors, cancellations and length-limited endings do not count. An idle avatar may briefly use a free printer or handset. This means a response finished in Pi, not that a file was printed, a call was made, or a task succeeded.
  • Engine vs skills: startup and work/settled hooks report presence. The session_before_compact hook reports compact_context. An available filing cabinet opens on arrival, and the avatar sorts books until compaction ends or a newer action takes over. Pi reports success, cancellation or failure without sending a summary, prompt or error message. An engine without a start hook should report only the outcome, not invent a start. A skill supplies instructions: the connector reports the tools Pi actually calls, not the skill name, its contents or a guessed start/end. Slash commands are not automatically tool events.
  • Meeting: a Pi UI prompt reports human.waiting; closing it reports human.resumed. A confirmation displays Yes / No; select and text prompts display their input type, not private choices. A custom dialog with no safe metadata displays only the wait. Only Pi can take the answer.
  • Lounge: explicit online idle without active work or human attention allows ambient stops. Coffee, water, aquarium and plants are cosmetic, not assignments.

A tool event may appear on a card without a journey: the scene debounces ordinary room changes for three seconds and operates props only after arrival.

pi-subagents: report an observed child, not a tool name

The Pi adapter handles a same-session, single asynchronous launch and its matching terminal receipt. It generates public UUIDv7 run IDs, retains the provider ID only in memory, and sends a child start linked to its active delegation run. Parallel/workflow containers, nested launches and foreground calls are not counted as single children. Listing, a failed launch without a start, a pause, or a tool returning an async handle is not a child lifecycle.

Example event inside the normal authenticated batch (the parent must already exist). The sender chooses the public avatar label and short task title; the panel chooses the station. Use a neutral label and task category when the real ones are private.

Choose a Credential and Build the Headers

Prefix each path below with your configured collector origin and /api/v1. Send exactly one bearer token, without quotes. Never follow redirects with credentials. No member cookie, CSRF token, share link, or model key is needed by the connector.

Authorization: Bearer <credential for this operation>
Content-Type: application/json
Accept: application/json
  • amo_join_ — enroll a general installation only while admission is Open. Rotation prevents new enrollment with the old key.
  • amo_producer_ — identify one installation; open, resume or permanently close its sessions. Trusted producers work in either mode. One producer supports multiple sessions.
  • amo_writer_ — heartbeat/events for exactly one agent and generation. Inbox operations additionally require the assigned-inbox grant. General writers never receive it.
  • amo_agent_ — legacy dedicated or simulator credential; there is no new dedicated-agent registration. Skip enrollment/open and use its assigned ID on reporting requests. Never share one dedicated credential across parallel sessions.

Send JSON as UTF-8; omit Content-Type on bodyless requests. On 204, do not parse JSON. Keep secrets in protected storage. Do not place them in URL parameters, event data, console output or error reports. Owner management uses separate authenticated dashboard endpoints.

Enroll and Open a Temporary Visit

For a general connector, generate a producer token and retain it in process memory before calling enrollment. For trusted connectors, skip enrollment. For each new session, generate and retain a separate in-memory writer token before opening. Each generated token is the indicated prefix followed by 32 cryptographically random bytes encoded as unpadded base64url (43 characters). Angle-bracket values below are placeholders, not usable secrets.

For example, in Node.js use prefix + randomBytes(32).toString("base64url") with randomBytes from node:crypto. Save the result privately; do not print it. Generate a fresh value for every new writer or rotation.

1. General Enrollment

POST /machine/enroll with the join bearer. The key selects the office. If your connector serves more than one office, GET the same path with that key to resolve its office_id before choosing the producer bound to that office. Keep the generated producer token; the reply returns its ID, not the secret. A lost reply can be retried with the same producer token and a valid join key.

{"producer_token":"<generated amo_producer_ token>", "visit":true}

Plugin settings vs. session data

The panel does not prescribe a plugin config file format. For a workspace-based connector, ask the operator for the panel URL and credential, not a project or office name. Retry and heartbeat settings are local plugin options. For example, a plugin might store these settings privately:

{"panel_url":"https://office.example.com", "token":"<office join key or trusted connector token>"}

Build the request below at session start. Set harness to the engine identifier and name to the working folder’s basename, not its full path. For example, a session in a folder named homelab displays as homelab. If a session has a title suitable for office viewers, the plugin can send it as project; otherwise it can omit that field. Neither label identifies the session or chooses the office.

2. Open

POST /machine/sessions with the producer bearer. Generate a unique visit ID and reuse it only for this live session, not a project, username or display name. Use session for interactive sessions and daemon for persistent workers.

{
  "visit": true, "harness": "my-engine", "external_session_id": "session-42",
  "name": "homelab", "lifecycle": "session",
  "writer_token": "<saved amo_writer_ token>"
}

Example response (201 new, 200 exact active retry):

{"agent_id":"019e0000-0000-7000-8000-000000000001","generation":1,"expires_at":"2026-11-18T10:30:00.000Z","last_seq":0}

Save the agent ID alongside the writer. The same project can have many agent IDs. When a project label changes, PATCH /machine/sessions/{agent_id}/project with the current writer bearer and {"project":"Release Notes"}. This changes the displayed project, not the identity. Start the next report at last_seq + 1.

Report Presence and Observed Work

Serialize writes per identity. Heartbeats and events share a single increasing positive safe-integer sequence, not separate counters. Use the writer bearer. A heartbeat declares presence, not a completed task.

Heartbeat

POST /agents/{agent_id}/heartbeat every 15–20 seconds under the default 30-second online threshold. An idle example for a newly opened identity:

{ "seq": 1, "state": "idle" }
Download heartbeat example (JSON)

Equivalent HTTP sender in JavaScript (assumes a validated origin, a trusted agent ID and a writer loaded from private storage):

const response = await fetch(`${origin}/api/v1/agents/${agentId}/heartbeat`, {
  method: "POST", redirect: "error", signal: AbortSignal.timeout(4000),
  headers: { Authorization: `Bearer ${writer}`, "Content-Type": "application/json" },
  body: JSON.stringify({seq: lastSeq + 1, state: "idle"})
});
if (!response.ok) throw new Error(`Heartbeat HTTP ${response.status}`);
const confirmedSeq = (await response.json()).seq;

Event Batch

POST /agents/{agent_id}/events. Generate a new lowercase UUIDv7 for each event and each run. Reuse the run ID from start to finish. Only send the example stages for events you actually observed; aborted work is not success.

{"events":[
  {"event_id":"019e0000-0001-7000-8000-000000000001","seq":2,"type":"run.started","run_id":"019e0000-0001-7000-8000-000000000002","data":{"title":"Check build","kind":"work"}},
  {"event_id":"019e0000-0002-7000-8000-000000000001","seq":3,"type":"tool.call","run_id":"019e0000-0001-7000-8000-000000000002","data":{"action":"read","tool":"read","ok":true}},
  {"event_id":"019e0000-0003-7000-8000-000000000001","seq":4,"type":"run.finished","run_id":"019e0000-0001-7000-8000-000000000002","data":{}}
]}

Example response: {"accepted":3,"duplicate":0,"rejected":[],"next_seq_hint":5}. Inspect each rejection even on HTTP 200. A timeout is not proof of failure: replay the original serialized event with identical fields, order, ID and sequence. Do not recreate it with a new ID. Bound and back off retries, keep terminal events until confirmed, and coalesce heartbeat ticks.

Other client signals: agent.registered/shutdown, plan.start/end, tool.start/end, run.failed, spawn.started/finished, human.waiting/resumed, error and note. A spawn signal is not a child identity. Human waiting is telemetry only; answers stay in the original engine. The server owns task.* events. Limits: 2 KB per heartbeat; 200 events and 64 KB per batch; 4 KB per event data object.

Renew, Reconnect or Retire

For temporary visits, reopen with the same in-memory ID and writer before lease expiry; use the returned ID and sequence. Do not replay an old event into a new visit after cleanup. The optional rotation protocol for connectors retaining a current writer works as follows. Writer leases last 15 minutes. Before expiry, POST /machine/sessions/{agent_id}/resume with the producer bearer. Save both old and next writer proofs privately before the request:

{"writer_token":"<current writer>","next_writer_token":"<newly generated writer>"}

The response has the open-response shape. Keep the same agent ID, adopt the returned sequence, switch to the new writer and discard the old one only after confirmation. Resume accepts an expired current writer as proof if the producer is still authorized. After an ambiguous result, confirm by opening the same external identity with the saved next writer. Never guess identity from a name or mint a replacement to bypass a denial.

For a temporary disconnect do nothing destructive. For permanent retirement only, DELETE /machine/sessions/{agent_id} with both Authorization: Bearer <producer> and X-Writer-Token: <current writer>, no body. A 204 archives the identity; it is not an ordinary shutdown hook.

401: verify origin, target and token role; check expiry, admission and revocation. 403: missing grant; do not escalate automatically. 409: check competing writers, closed identity, sequence or capacity; do not spin. 413: reduce payload size. Bound requests with a timeout. Never treat collector downtime as a successful run or task acknowledgement.
